# Отчет: Анализ алгоритма поиска маршрутов с пересадками

**Дата анализа:** 16 ноября 2025
**Анализируемая система:** Bus Route Planning Backend (Spring Boot 3.5 + R2DBC + PostgreSQL/PostGIS)

---

## 1. Исходное техническое задание

### Проблема
Необходимо проверить, поддерживает ли алгоритм построения маршрутов пересадки с изменением направления движения (когда пассажир пересаживается на автобус, движущийся в обратном направлении, часто требуя перехода на противоположную сторону дороги).

### Тестовый сценарий
- **Точка A:** Широта 37.897419, Долгота 58.387463
- **Точка B:** Широта 37.928600, Долгота 58.353302
- **Расстояние между точками:** 4.58 км (по прямой)

## 3. Анализ SQL-запроса для поиска маршрутов с одной пересадкой

### 3.1. Структура запроса

Файл: `R2dbcRouteSearchRepository.java:208-367`

Запрос состоит из **4 UNION ALL секций**, покрывающих все комбинации направлений:

#### Комбинация 1: Forward-Forward (FF)
```sql
-- Оба маршрута в прямом направлении
WHERE rs1_start.direction = 0 AND rs1_end.direction = 0
  AND rs2_start.direction = 0 AND rs2_end.direction = 0
```

#### Комбинация 2: Forward-Backward (FB) ⚠️
```sql
-- Первый маршрут прямо, второй обратно - СМЕНА НАПРАВЛЕНИЯ!
WHERE rs1_start.direction = 0 AND rs1_end.direction = 0
  AND rs2_start.direction = 1 AND rs2_end.direction = 1
```

#### Комбинация 3: Backward-Forward (BF) ⚠️
```sql
-- Первый маршрут обратно, второй прямо - СМЕНА НАПРАВЛЕНИЯ!
WHERE rs1_start.direction = 1 AND rs1_end.direction = 1
  AND rs2_start.direction = 0 AND rs2_end.direction = 0
```

#### Комбинация 4: Backward-Backward (BB)
```sql
-- Оба маршрута в обратном направлении
WHERE rs1_start.direction = 1 AND rs1_end.direction = 1
  AND rs2_start.direction = 1 AND rs2_end.direction = 1
```

### 3.2. Ключевой JOIN для пересадки

```sql
JOIN route_stops rs2_start ON rs1_end.stop_id = rs2_start.stop_id
                           AND rs2_start.direction = [0 или 1]
```

**Критическая деталь:** Соединение происходит только по **точному совпадению `stop_id`**.

### ✅ Что работает правильно

1. **Алгоритм теоретически поддерживает смену направления**
   - SQL-запрос включает комбинации FB и BF
   - Все 4 комбинации направлений (FF, FB, BF, BB) реализованы

2. **Параметры поиска настроены корректно**
   - Радиус поиска остановок: 800м
   - Максимум пересадок: 2
   - Время ожидания: 30 минут

3. **База данных содержит достаточно данных**
   - 1,041 остановка
   - 97 активных маршрутов
   - Покрытие тестовых точек (остановки в пределах 60м)

### ⚠️ Обнаруженные ограничения

#### Проблема 1: Жесткое требование `stop_id`

**Описание:**
Алгоритм требует **точного совпадения `stop_id`** для пересадки:

```sql
JOIN route_stops rs2_start ON rs1_end.stop_id = rs2_start.stop_id
```

**Последствия:**
- ❌ Пересадки между **близлежащими остановками** (10-100м) не обнаруживаются
- ❌ Переходы через дорогу (на противоположную остановку) не учитываются
- ❌ Реальные пересадочные возможности упускаются

**Пример из БД:**
Остановки "Bahar" dükany с `stop_id` A и B находятся в 12 метрах друг от друга (противоположные стороны улицы), но алгоритм считает, что между ними нельзя сделать пересадку.

#### Проблема 2: Специфика тестовых координат

**Результат теста:**
```bash
curl -X POST http://localhost:8080/api/v1/trip-planning/search \
  -d '{"from": {"lat": 37.897419, "lon": 58.387463},
       "to": {"lat": 37.928600, "lon": 58.353302}}'

Ответ: "error_type": "NO_ROUTE_FOUND"
```

**Причины:**
1. Расстояние между точками: **4.58 км**
2. Зона A обслуживается 14 маршрутами (14, 18, 20, 23, 26, 29, ...)
3. Зона B обслуживается только 2 маршрутами (55, 57)
4. **Маршруты не пересекаются** - нет общих остановок даже в радиусе 500м
5. Требуется как минимум **2 пересадки** (но возможно и больше)

**Вывод:** Для данных конкретных координат маршрут с одной пересадкой действительно не существует в сети общественного транспорта. Это **НЕ ошибка алгоритма**, а реальность маршрутной сети.

## 6. Рекомендации

### 6.1. Критичное улучшение: Поддержка пересадок между близлежащими остановками

#### Предлагаемое решение

Изменить JOIN в SQL-запросе с точного совпадения на **геопространственный поиск**:

**Было:**
```sql
JOIN route_stops rs2_start ON rs1_end.stop_id = rs2_start.stop_id
```

**Должно быть:**
```sql
JOIN route_stops rs2_start ON rs2_start.stop_id IN (
    SELECT bs2.id
    FROM bus_stops bs1
    JOIN bus_stops bs2 ON ST_DWithin(
        ST_SetSRID(ST_MakePoint(bs1.longitude, bs1.latitude), 4326)::geography,
        ST_SetSRID(ST_MakePoint(bs2.longitude, bs2.latitude), 4326)::geography,
        :transferRadius  -- например, 100 метров
    )
    WHERE bs1.id = rs1_end.stop_id
      AND bs2.is_active = true
)
```

**Параметры:**
```yaml
business:
  routing:
    transfer-radius: 100  # Максимальное расстояние пешего перехода между остановками (метры)
```

#### Преимущества

1. ✅ Обнаружение пересадок через дорогу
2. ✅ Учет пешеходных переходов между близкими остановками
3. ✅ Более реалистичное моделирование поведения пассажиров
4. ✅ Увеличение количества найденных маршрутов

#### Потенциальные риски

1. ⚠️ Увеличение времени выполнения запроса (требуется индекс на геопространственные данные)
2. ⚠️ Необходимость добавления расчета времени пешего перехода в общее время маршрута

### 6.2. Оптимизация производительности

**Рекомендация:** Создать материализованное представление (materialized view) для пар близлежащих остановок:

```sql
CREATE MATERIALIZED VIEW nearby_stop_pairs AS
SELECT
    bs1.id as stop_id_1,
    bs2.id as stop_id_2,
    ST_Distance(
        ST_SetSRID(ST_MakePoint(bs1.longitude, bs1.latitude), 4326)::geography,
        ST_SetSRID(ST_MakePoint(bs2.longitude, bs2.latitude), 4326)::geography
    ) as distance_meters
FROM bus_stops bs1
JOIN bus_stops bs2 ON bs1.id < bs2.id
WHERE ST_DWithin(
    ST_SetSRID(ST_MakePoint(bs1.longitude, bs1.latitude), 4326)::geography,
    ST_SetSRID(ST_MakePoint(bs2.longitude, bs2.latitude), 4326)::geography,
    100
)
AND bs1.is_active = true
AND bs2.is_active = true;

CREATE INDEX idx_nearby_pairs_stop1 ON nearby_stop_pairs(stop_id_1);
CREATE INDEX idx_nearby_pairs_stop2 ON nearby_stop_pairs(stop_id_2);
```

Обновление: ежедневно или при изменении остановок.
